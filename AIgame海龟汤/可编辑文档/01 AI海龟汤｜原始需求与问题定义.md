# 01 AI海龟汤｜原始需求与问题定义

版本 V0.1｜审阅稿｜2026-10-22。

一句话问题定义：想独自或与朋友玩海龟汤的玩家，需要通过问答还原故事；真人主持需要提前掌握答案且会影响游戏质量，产品希望让玩家不依赖真人主持也能完成公平的推理与揭晓。需求来自产品发起人的体验和选择，尚未通过外部用户研究验证普遍性。

文档状态：原始诉求和主要产品选择已记录，用户问题的强度、发生频率与付费意愿尚未验证。

## 1. 需求基本信息

| 项目 | 内容 |
|---|---|
| 需求名称 | AI 海龟汤主持与多人协作推理 |
| 提出方 | 本次对话中的产品发起人；真实姓名与组织未采集 |
| 提出方式 | 多轮文字共创，并逐项确认 |
| 整理日期 | 2026-10-22，沿用本次会话日期，不推定每条消息独立时间 |
| 目标用户 | 中国大陆中文海龟汤玩家；单人玩家与组局玩家 |
| 核心需求 | 无需真人主持，也能围绕固定真相提问、得到一致回答并完成揭晓复盘 |
| 当前阶段 | 文档与验证方案准备；尚未开始游戏制作和真实用户内测 |

## 2. 需求背景

| 背景维度 | 原始材料记录 | 当前判断 |
|---|---|---|
| 发起动机 | 用户希望做一款上线后持续运营的 AI game | 目标包含持续内容供给与运营，并非一次性技术演示 |
| 产品切口 | 用户提出 AI 替代真人海龟汤主持人 | 应先验证主持可靠性与完整游玩价值 |
| 体验判断 | 用户认为好不好玩取决于汤面与主持人专业程度 | 用户体验观点；题目与主持需分别评价，不能只测模型 |
| 成本设想 | 用户认为纯文字成本相对低 | 可减少部分素材工作，但总成本仍含题目审校、模型、运营和发布条件 |
| 内容偏好 | 微恐惊悚、允许变格，加入匹配的纯音乐 | 已确认产品定位，不等于整个市场的偏好 |

## 3. 用户角色

| 角色关系 | 具体角色 | 在需求中的位置 |
|---|---|---|
| 使用者 | 单人玩家 | 自己开房，与 AI 进行完整推理 |
| 使用者 | 多人参与玩家 | 共同讨论、正式提问、投票和提交推理 |
| 房间管理者 | 房主 | 管理房间、选择题目和开局；不能因此看到汤底 |
| 旁观者 | 开局后加入者 | 旁观当前对局，下局参与；细化权限见 PRD 待评审项 |
| 服务提供者 | AI 主持与程序规则系统 | 前者做语义判断，后者执行权限、投票与计时 |
| 内容供给与审核者 | 题目编辑／产品运营角色 | 维护固定答案、事实边界、提示与质量反馈；人员待指定 |

同一个人可能在不同房间或阶段承担不同角色，不将角色数量当成人群规模。

## 4. 业务场景与用户任务

主要任务是从好奇的汤面出发，通过有限问答还原因果，并在揭晓复盘后获得完整解释。以下场景为依据产品诉求的归纳，不是外部访谈结果。

| 场景 | 任务与触发 | 频率/业务量 | 目标结果 |
|---|---|---|---|
| 独自想玩 | 无需组人或找到知晓答案的主持人，直接开始 | 实际频率未知 | 完成一次有逻辑、公平的推理 |
| 朋友组局 | 希望所有朋友都能参与猜谜 | 实际组局频率未知 | 不需要一人提前看答案并退出猜谜角色 |
| 加入公开房 | 暂无固定朋友在线，想找到一起玩的玩家 | 需求强度待验证 | 看懂房间状态，进入等待房或旁观 |
| 卡关 | 长时间未推进，需要帮助但不想被剧透 | 尚无卡关日志 | 按约定逐层获得提示 |
| 内容运营 | 需要持续补题和修复主持错误 | 首批题库设定 12 道 | 能追溯问题、修订题目而不改动当前局真相 |

## 5. 当前流程

用户提供的是“真人主持人规范流程”，不是对某场真实对局的观察记录。其概括为：主持读透汤底并约定规则 → 公布汤面 → 玩家提问与主持判定 → 提示与解答判断 → 揭晓 → 复盘 → 换题。

| 环节 | 谁做 | 实际做法 | 产出 |
|---|---|---|---|
| 准备 | 真人主持 | 按用户提供的规范先看懂答案并选题 | 主持掌握真相 |
| 开场 | 主持与玩家 | 约定人数、时长、次数、回答范围 | 共同规则 |
| 推理 | 玩家与主持 | 玩家是非提问，主持根据汤底回答 | 已验证或排除的线索 |
| 帮助 | 主持 | 判断是否偏题、冷场和需要提示 | 引导或新线索 |
| 收尾 | 主持 | 判断解答，揭晓并解释关键因果 | 完整故事与复盘 |

尚未取得一次最近真实游玩的完整时间线、等待时长、错误回答或组局失败记录。

## 6. 问题发生位置与影响

| 问题位置 | 现有证据 | 具体问题 | 造成的影响 |
|---|---|---|---|
| 开局前 | 发起人明确希望不需要真人主持 | 需要有人提前知晓答案 | 主持组织负担和单人开局障碍属于待验证影响 |
| 推理中 | 发起人重视主持专业性 | 错误或前后矛盾的判定可能破坏推理 | 公平性受损是分析判断；实际频率未知 |
| 提示时 | 用户同时提出四词回答与节奏引导 | 判定与提示混在一起会额外泄露信息 | 已通过分开判定与提示通道解决产品规则冲突 |
| 收尾 | 用户明确复盘结束才算结束 | 只揭晓、不解释，可能缺少理解与成就感 | 待通过复盘观察验证 |
| 运营 | 用户希望持续上线 | 已知答案的题目通常失去首次推理空间 | 内容更新速度、重复游玩价值仍未知 |

## 7. 业务方希望改变什么

| 从当前状态 | 希望变成 | 尚未决定 |
|---|---|---|
| 依赖真人主持准备和判定 | 单人或全员参与的多人局可由系统主持 | 实测可靠性、与真人基线的差异 |
| 主持质量依人而异 | 固定答案、明确事实边界和可追溯反馈 | 模型最终选择、错误修复规则 |
| 手动组织与散落聊天 | 房间内分开讨论与正式提问 | 部分断线、观战和记录权限细节 |
| 只有一次体验 | 运营题库并验证再次游玩动机 | 内容生产成本、重复使用与付费价值 |

## 8. 待调研验证事项

| 必须回答的问题 | 当前缺口/冲突 | 需要取得的证据 |
|---|---|---|
| 谁最需要无人主持 | 目前只有发起人自述和产品选择 | 近期游玩经历访谈，纳入不感到困扰的玩家 |
| AI 能否公平主持 | 尚无专项测评 | 人工标注问题集、多轮一致性与解答对照测试 |
| 用户为何再次来玩 | 新鲜感可能不同于持续价值 | 不同题目下真实回访与主动开下一局记录 |
| 多人是否值得增加复杂度 | 用户要求两种方式均有，净增益未测 | 单人与多人分开观察完成、放弃及协调成本 |
| 内容与技术是否可持续 | 缺少人工工时和真实用量 | 每题审校记录、每局账单、故障处理时间 |
| 可以怎样对外测试 | 服务性质、主体、备案等未核实 | 相应专业／主管渠道核实结果与可执行发布路径 |
