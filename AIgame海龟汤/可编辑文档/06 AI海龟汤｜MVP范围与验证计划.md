# 06 AI海龟汤｜MVP范围与验证计划

版本 V0.1.1｜范围承接已确认决策；验证门槛为审阅建议｜2026-10-23。

## 1. 核心假设与执行前提

H1：通过经过审核的混合惊悚题库和受约束 AI 主持，目标玩家可以在单人或多人环境中完成公平、完整的推理，并愿意主动再玩一道未知答案的新题。

支持假设为主持可稳定判定、多人协作不破坏公平、题目供给可持续、费用可控。H1 尚未验证；模型可接入、需求已确认不代表 H1 成立。

本 MVP 指邀请码完整内测版，不是只有聊天界面的技术样例。用户明确要求单人和多人、搜索与匹配均有，范围不因“最小”而擅自删减。可以先做离线题目／模型验证，再实现完整范围；制作须等待明确开始指令。

## 2. 明确不做及理由

| 排除项 | 本版不做的理由 |
|---|---|
| 支付、会员、广告 | 当前目标免费验证公平与完整体验，尚无购买证据 |
| 无限时间／无限提问 | 与免费预算、并发名额和收尾预留冲突 |
| 即时生成未审题、玩家投稿 | 会混淆题目问题和主持错误，增加审核负担 |
| 原生 App、多语言 | 当前已确认中文移动网页，避免扩大平台投入 |
| 语音主持、语音聊天、实时音乐生成 | 超出纯文字加预设纯音乐的首版范围 |
| 排行榜、战力成长、AI 假玩家 | 与共同破案的主假设无必要关系，不伪造匹配供给 |

## 3. 最小完整流程

邀请码注册与登录 → 可跳过教学 → 创建／加入房间 → 房主选题配置 → 公布完整汤面 → 讨论、正式提问、提示、提交推理 → 成功或规则耗尽 → 揭晓与复盘 → 反馈和记录 → 回原房继续。

后台提供审核题目、发布和修复的最小闭环。没有后台与反馈，无法持续修正题目和主持问题；没有真实费用记录，无法检验预算约束。

## 5. 交付验收与假设验证分开

交付验收检查功能是否按规定工作。假设验证检查真实玩家有没有获得价值。按钮可点、模型能返回 JSON、8 个房间打开成功，都不能证明玩家愿意持续玩。

| 验证项 | 对象与方法 | 指标口径 | 支持／调整／停止判断 |
|---|---|---|---|
| 主持质量 | 审核题目集、人工标准答案、换问法多轮与解答对照 | 有效问题判定准确率、矛盾率、泄底次数、误判通关次数分开统计 | 严重错误先修复；具体目标见 08 的建议门槛 |
| 完整任务 | 单人和真实多人局分别回放 | 从汤面展示到复盘结束；成功、耗尽、离开、故障分开 | 主路径或收尾经常失败先修复，不扩大邀请 |
| 重复价值 | 邀请玩家自然使用，另题与跨日观察 | 主动开始另一道未玩题；排除工作人员引导、测试账号和重复刷新 | 有行为再扩大；没有行为先访谈原因；样本不足不宣称失败 |
| 多人增益 | 熟人局和公开房分别观察 | 提问／讨论贡献分布、等待与退出原因 | 多人只剩少数人参与时调整协作，不擅自删掉多人需求 |
| 成本与产能 | 实际请求账单与内容制作记录 | 每局实际技术成本、每道可用题的人工与素材投入 | 预算不可持续先调整规模／模型；内容成本须进入商业判断 |

观察窗口、真实样本数和留存／付费阈值未确定，待首批基线与用户招募计划形成后再定，不套用无依据行业数值。先完成离线质量与功能验收，再进行真实使用观察。

## 6. 以后再说及重启条件

题包收费在主持可靠、回访与供给稳定后研究；订阅在更新承诺可兑现后研究；App 在网页价值成立且存在明确平台需求后研究；自动生成与投稿在审核体系稳定并确认供给缺口后研究。不承诺下一版本日期。

## 7. 尚需评审的实施细节

重连与保留席位、观战只读和容量、踢出重入、记录可见性、预算分配与限额、服务时延门槛、数据保留和发布条件。这些已在 07、08、09 标为建议或待核实，不改变已确认主玩法。


2026-10-23 本地修订：用户要求不预告本格／变格，分类改为主持与审核内部字段；保留正常提问判定。选题保留推理难度、恐怖强度及不泄底的描述尺度。
